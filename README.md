# MyNaksh — AI Conversation Experience

A React Native CLI (TypeScript) implementation of the MyNaksh AI conversation
screen: a chat timeline that can render composable "recommendation experiences"
(gemstone, tarot, consultation, article, promotion) inline with AI responses, plus
production chat interactions (reply/copy/delete, like/dislike feedback, optimistic
send with retry, loading/empty/error states). Built on the bare React Native CLI
(not Expo) with React Native Reanimated driving the feedback-chip animation, per
the assignment's stated primary stack.

## Running it

```
npm install
cd ios && pod install && cd ..
npx react-native run-ios      # or: npx react-native run-android
```

Verified booting cleanly on iOS Simulator (iPhone 17, iOS 26.5). Android requires
an Android SDK/emulator set up locally (not available in the environment this was
built in) — the app code has no platform-specific branches, so it's expected to
run the same way via `npx react-native run-android` once a device/emulator is
available; if you hit an issue there, it's almost certainly a local toolchain
problem, not an app bug.

## Component architecture

Each message author (`system`/`user`/`ai`/`human`) has its own small bubble
component rather than one branching mega-component — this matches the "reusable
message components" requirement and keeps each file easy to reason about and
style independently. `MessageList` stays dumb: it turns the raw message array into
a flat timeline (via `buildTimelineItems`) and dispatches to the right bubble by
`message.type`. All list rendering (timeline + each recommendation rail) uses
`FlatList` for virtualization.

Message actions (Reply / Copy / Delete) are triggered by long-press and shown in a
single reusable `MessageActionsSheet` (plain `Modal`, no extra library), fed a
per-bubble `actions` array — adding a new action to any bubble type is a one-line
array entry.

## State management approach

**Zustand** (`src/store/conversationStore.ts`) — one flat store holding
`status` (`loading`/`ready`/`error`), `messages`, and `replyTarget`, with plain
async functions as actions (`loadConversation`, `sendMessage`, `retryMessage`,
`deleteMessage`, `setReplyTarget`, `setFeedback`). This was chosen over Redux
Toolkit / Context because the scope doesn't need reducers, middleware, or a
Provider tree — Zustand lets optimistic-update logic (append → simulate delay →
patch status) live as a single readable function per action, and components
subscribe to only the slices they need (`useConversationStore(s => s.messages)`)
so unrelated state changes (e.g. composer text, which is local `useState`) don't
re-render the list.

## Recommendation rendering strategy

This is the core extensibility requirement, solved with a **registry pattern**
(`src/components/recommendations/registry.tsx`):

```ts
RECOMMENDATION_REGISTRY: Record<RecommendationType, ComponentType<{item}>>
```

`RecommendationRail` (horizontal `FlatList`) looks up each recommendation's card
component by `item.type` via `resolveRecommendationCard`, falling back to a
generic card for any type the client doesn't recognize yet (forward-compatible
with "future AI-powered experiences" from the brief). Per-type cards
(`GemstoneCard`, `TarotCard`, …) are thin — they just supply an icon/accent color
to the shared `RecommendationCard` shell and share one `onPress` behavior
(`Alert.alert`).

**To add a new recommendation type:** add it to the `RecommendationType` union,
create one card component, add one line to the registry. No changes needed to
`MessageList`, `AiMessageBubble`, or `RecommendationRail` — this is the direct
answer to "easy to extend with future recommendation types."

## Performance considerations

- `FlatList` (not `ScrollView`) for both the main timeline and every horizontal
  recommendation rail — virtualized rendering regardless of conversation length.
- `React.memo` on all bubble/card/row components; stable `keyExtractor`s by id.
- Zustand selector subscriptions are granular, so typing in the composer (local
  `useState`) never re-renders the message list, and a feedback toggle on one
  message doesn't re-render others.
- `buildTimelineItems` (date separators + message grouping) is computed once via
  `useMemo` keyed on the messages array, not per-render per-item.

## Trade-offs made due to time constraints

- **Icons via `react-native-vector-icons` instead of a managed asset pipeline.**
  Bare RN CLI has no Expo-style auto asset bundling, so Ionicons' font is linked
  manually: `UIAppFonts` entry in `ios/MyNakshCLI/Info.plist` (iOS bundles the
  font automatically via CocoaPods otherwise) and `fonts.gradle` applied in
  `android/app/build.gradle` (Android). A production app would likely use a
  per-icon-family package instead (the library's maintainers now recommend
  this), but the monolithic package was faster to wire up for this scope.
- **Clipboard via `@react-native-clipboard/clipboard`** instead of
  `expo-clipboard` — same `setString`-style API, swapped at the three bubble
  components that expose the Copy action.
- **Synthetic timestamps.** The spec's mock payload has no timestamps, so
  sequential synthetic ones were assigned at seed time purely to drive date
  separators/grouping — a real backend would supply these.
- **Simulated network layer.** `sendMessage`/`retryMessage` use a fixed-delay
  `setTimeout` with a random success/failure split (not a real API) to
  demonstrate the Sending → Sent/Failed → Retry states.
- **No persistence.** State lives only in memory (Zustand, no AsyncStorage) —
  acceptable per "backend integration is not required."
- **Feedback chips are single-message-scoped** — no backend sync, just local
  state, per the spec's "selecting a chip should update local state."
